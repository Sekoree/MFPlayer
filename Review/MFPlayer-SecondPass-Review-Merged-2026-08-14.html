This document contains the second reviewer's own findings (N-xx), rendered-UI evidence, and — at the end — a comparison with Review/MFPlayer-Comprehensive-Review-2026-08-14.html (F-01…F-24) and a merged finding index and roadmap.

Executive summary

This is an unusually disciplined codebase. The engine, session, routing and core layers show many completed hardening passes: reader-lease disposal patterns, bounded queues everywhere, lock-free clock republishing, exhaustive "why" comments citing real incidents, a dedicated session dispatcher with continuation pumping, and ~4,400 green tests. A deliberate bug-hunt through ShowHost, CueExecutor, AudioPatchBay, SessionDispatcher and FrameAlignedFloatRing found the well-known races already handled.

What this pass adds: one High-severity fault path that can stop the show engine from starting (N-01, corrupt idle-image aborts reload and leaks devices), a cluster of Medium issues in the newer, less-audited seams (an unguarded CTS race in OutboundEffects, a probe cache that never notices a replaced media file, a hard-coded output name in an operator-facing warning), a set of UI-thread render-efficiency improvements common to both apps, and rendered screenshots of the HaCue2 surfaces — which the previous review could not capture on its host.

On the previous review: its center of gravity (package restore truth, FFmpeg provenance, save-race F-03, cancellation-scope F-04, remote-server boundedness F-05) is sound and complementary — almost no overlap with this pass's findings. Where this pass could re-check its claims (F-16, F-18, F-21, F-05, F-03 code paths), they held up. The merged index below is the union.

What is genuinely strong (do not disturb)

  • Ownership and disposal discipline. SDL3GLVideoOutput.Submit's dispose-race recheck, AutomationRun's reader-lease pattern, PreparedFollow's reservation-before-open, and AudioPatchBay's prepared-terminal staging are textbook. The same idioms recur; the codebase has a house style for lifecycle races and mostly applies it (N-02 is the one seam that missed it).
  • The engine/UI separation in HaCue2 (ICueExecutionHost + CueExecutor) makes the code with "the most at stake" testable without devices, and the tests are actually there (445 in HaCue2.Tests, 781 in Core.Tests).
  • Comments explain intent and cite incidents. This is rare and worth protecting in review culture: most comments answer "why is it this way and what broke before", not "what does the next line do".
  • Zero-warning builds with analyzers + AOT compat on, architecture tests enforcing layer direction, and central package management.
  • Operator-first product decisions: panic-as-short-fade, sounding-from-GO-press, held-edit deferral with visible hint, black-as-a-real-answer idle frames, fixed-time token comparison and refuse-when-tokenless in the remote API.

New findings (N-01 … N-13)

HIGH N-01 · A corrupt or unsupported idle image aborts the whole document reload — and can stop the engine from starting

ShowHost.DecodeIdleAsync (UI/HaCue2.Engine/ShowHost.IdleFrames.cs:140) catches IOException, UnauthorizedAccessException, InvalidOperationException, NotSupportedException, ArgumentException — but the decode path throws two types outside that list:

  • FFmpegException — VideoFileDecoder.Open/TryReadNextFrame throw it for any file FFmpeg rejects (S.Media.FFmpeg.Common/FFmpegException.cs:5 — it derives directly from Exception);
  • InvalidDataException — thrown by this method's own lambda when the image produces no frame (ShowHost.IdleFrames.cs:131), and it is not an IOException.

Failure scenario. An operator points a composition's idle image (or an output's idle fallback) at a file FFmpeg can't decode — a truncated PNG, a PSD, a file renamed to .jpg. The exception escapes DecodeIdleAsync, aborts ApplyIdleFramesAsync, and propagates out of ReloadAsync:

  • Mid-show: the reload dies halfway — screens have been synced but triggers, recorders, actions and calibration restore never run for that pass; the shell shows "engine reload failed" and the edit is effectively lost until another edit retriggers a reload.
  • At startup: ShowHost.StartAsync throws before returning the host, so the engine never starts ("the show engine could not start" in the status bar, UI/HaCue2/App.axaml.cs:310–315) — and because the host is never returned, the already-opened audio bay, session and windows are never disposed (device leak until process exit).
Long-term fix. Idle-frame decoding is best-effort by design — make the code say so. Broaden the filter to catch (Exception e) when (e is not OperationCanceledException and not OutOfMemoryException) (the method already reports by name), and additionally wrap the tail of ReloadAsync's per-subsystem steps so one failing step reports and continues rather than aborting its siblings. For the startup path, make StartAsync dispose the partially-built host on any exception (a try/catch { await host.DisposeAsync(); throw; } around the reload). Add a regression test that loads a project whose idle path points at a text file.

MEDIUM N-02 · OutboundEffects disposes a run's CTS while it is still discoverable — Interrupt/Complete can throw on an engine thread

In DriveAsync's finally (UI/HaCue2.Engine/OutboundEffects.cs:209) the run's CancellationTokenSource is disposed before the run is removed from _running under the gate. Interrupt (:117), Complete (:146) and DisposeAsync (:329) all look the run up under the gate, then call Cancellation.Cancel() outside it — so a run finishing at that moment throws ObjectDisposedException into the caller. Callers include Forget() on session event threads (VoiceEnded/ClipTailEnded), where an unhandled throw is at best an unobserved task exception and at worst kills the delegate chain for that event.

Notably, the rest of the engine already solves this exact shape — AutomationRun's reader-lease discipline and CueExecutor's try { Cancel(); } catch (ObjectDisposedException) {} guards exist for this reason. This one class predates or missed the idiom.

Long-term fix. Either (a) remove the run from _running before disposing the CTS in DriveAsync's finally (order swap — the cheap fix that closes most of the window), plus wrap the three Cancel() call sites in the same ODE guard the rest of the engine uses; or (b) adopt the existing lease pattern. A small unit test that races Complete() against a run's natural end will pin it.

MEDIUM N-03 · MediaFactsCache never re-probes a path — a replaced media file keeps its stale duration and stream facts for the whole session

UI/HaCue2/Session/MediaFactsCache.cs:177 — Refresh skips any path already in _byPath, permanently. The cache key is the path alone. But re-exporting a file over the same path is the normal workflow during production ("the video got re-rendered, same filename"). After that:

  • the probed duration is stale → the compiler converts out-points against the wrong length (EndOffset in ShowCompiler.cs:387), timeline straddle math and the Active-panel lengths are wrong;
  • the resolved track indices/signatures are stale → a re-mux that reordered streams silently plays the wrong track;
  • a file that was broken and then fixed stays marked broken (and vice versa) until app restart.

The repo already states the correct policy elsewhere: WaveformCache keys on path + length + mtime specifically because "a re-encoded file at the same path must not read back the old shape" (UI/HaCue2.Machine/WaveformCache.cs:15). The probe cache contradicts it.

Long-term fix. Store (Length, LastWriteTimeUtc) beside each cached MediaFacts and treat a mismatch during Refresh as "not looked at yet" (the stat is one syscall per referenced file per refresh — Refresh already runs on every journal change, so keep the stat but debounce a full re-stat pass to save/open/window-focus if profiling ever shows it). This also gives the operator a working "the file changed, lengths updated" experience with zero new UI.

MEDIUM N-04 · Operator-facing warning names the wrong output: "No device channel receives Lobby" is hard-coded

UI/HaCue2/Views/AudioView.axaml:160 — the unpatched-logical-output warning in the Audio inspector is a literal string: "No device channel receives Lobby on this machine…", shown whenever IsSelectedOutputUnpatched — regardless of which output is selected. In the screenshot below the selected output is Sub and the red warning confidently talks about Lobby. During a "why is there no sound" moment this actively misdirects the operator toward the wrong bus.

Headless-rendered Audio workspace: row "Sub" is selected (inspector header SUB), the warning names "Lobby".

Long-term fix. Bind the message through the view-model (e.g. an UnpatchedWarning string computed from OutputName), and — as the previous review's F-21 argues more generally — move operator copy into typed resources so a literal like this can't hide in markup. A cheap guard: the existing headless render tests can assert the selected output's name appears in the warning text.

MEDIUM N-05 · UI render hot paths redraw everything and allocate per frame (HaCue2 WaveformGraph, HaPlay TimelineCanvas, Active-panel rebuild)

Three instances of the same theme, all on the UI thread of a live show:

  • WaveformGraph.Render (UI/HaCue2/Controls/WaveformGraph.cs:210–271) issues one FillRectangle per pixel column (600–1600 draw calls) and allocates two wash brushes per pass (Dim()). Playhead is in AffectsRender, so every playhead tick re-folds the peak buckets and re-draws every column even though only a 1-px line moved.
  • TimelineCanvas.Render (HaPlay, UI/HaPlay/Views/Controls/TimelineCanvas.cs:247+) allocates SolidColorBrush/Pen/FormattedText/PolylineGeometry per lane item per pass — during playback with a moving playhead this is steady GC churn exactly where frame-time matters.
  • CuesViewModel.Tick (UI/HaCue2/ViewModels/CuesViewModel.cs:1760) clears and refills the ActiveCues ObservableCollection four times a second — one CollectionChanged per removed plus per added row, so every tick re-realizes the Active panel's item containers even when the same cues are sounding.
Long-term fix. (1) Split static content from moving overlays: render peaks/lane blocks into a cached layer (a StreamGeometry/RenderTargetBitmap keyed on data + size + trim) and let the playhead invalidate only itself — Avalonia composition makes the two-visual split (waveform child control + overlay control) the simplest robust form. (2) Promote shared immutable brushes/pens to static readonly (Avalonia's ImmutableSolidColorBrush/ImmutablePen). (3) In Tick, diff by cue id and update mutable row VMs in place; add/remove only rows that actually changed. None of this changes behavior; all three are mechanical and test-safe.

MEDIUM N-06 · SessionRecoveryService blocks the UI thread with GetAwaiter().GetResult() during shutdown (HaPlay)

UI/HaPlay/Services/SessionRecoveryService.cs:413–451 — FinalizeCleanShutdown is documented as "UI thread, called from app teardown" and synchronously blocks on _activeCapture and CaptureCoreAsync(...). If anything inside the in-flight capture ever marshals to the UI thread (a Dispatcher.InvokeAsync, a continuation captured on the UI context before an await without ConfigureAwait(false)), shutdown deadlocks with the window half-closed. Today the capture path appears to stay on the pool, so this is a design risk, not a demonstrated hang — but it is one refactor away from being one, and WriteSessionInfo has the same shape.

Long-term fix. Make finalize genuinely async (the closing handler in HaPlay already awaits other teardown), or hand the final capture to a dedicated thread and wait with a bounded timeout + log. At minimum, add an analyzer suppression comment documenting the no-UI-marshal invariant the blocked-on code must keep, so the constraint is visible at the call sites it binds.

LOW N-07 · ProjectVideoOutputs._failures grows without bound across reloads (and double-records window-open failures)

UI/HaCue2.Engine/ProjectVideoOutputs.cs:283 — every Sync appends this pass's failures to the member list and nothing ever clears it. With a persistently failing output and the 300 ms edit-debounced reload, an evening of editing accumulates hundreds of duplicate strings. OpenWindow additionally writes its own entry into _failures (:325) and the caller records "could not open a window" into the per-pass list — two rows per event. Nothing user-facing reads the accumulated list after startup (only the per-pass return value), so today this is memory + a misleading first-report at StartAsync; it becomes a real bug the moment anyone binds Failures to UI.

Long-term fix. Make Failures mean "failures of the last sync" (replace, not append) and de-duplicate OpenWindow's bookkeeping so each failure is recorded exactly once, in one place.

LOW N-08 · AutomationRunClock.WaitUntilAsync polls at 1–5 ms regardless of distance to the target

UI/HaCue2.Engine/AutomationRunClock.cs:60–74 — a timeline run waiting ten minutes for its next authored edge wakes 200×/second the whole time (and DriveVisualizerAutomationAsync/DriveAutomationAsync tick their own 25 ms loops on top). Pause-awareness makes a pure sleep impossible, but the poll can be two-tier: while remaining > 1 s, sleep min(remaining/2, 250 ms); inside the last second, fall to the current 1–5 ms fine poll. Dispatch lateness (already measured by RecordTimelineDispatch) stays identical because the final approach is unchanged; idle CPU on a show with long timelines drops to noise.

LOW N-09 · ProjectPatchBay._open is mutated without a lock while other threads iterate it

UI/HaCue2.Engine/ProjectPatchBay.cs:44,298,449,464 — Apply iterates _open (UI-thread patch edits, patch-cue ramps on pool threads), while AttachRecorder/DetachRecorder add/remove entries (arm/disarm from the UI). The class has no gate over the list; the underlying AudioPatchBay does its own locking but this list doesn't. A patch ramp running while the operator arms a recorder is a realistic concurrent pair → InvalidOperationException: collection was modified mid-ramp. Low likelihood, easy fix.

Long-term fix. Guard _open (and the solo state, which already has its own lock) with one Lock, or snapshot (ToArray) before iterating in Apply.

LOW N-10 · StopTimelineAsync stops direct children only — a nested group's descendants can keep sounding

UI/HaCue2/ViewModels/ShellViewModel.cs:580–591 — the timeline sheet's ⏹ iterates group.Children. A timeline whose child is itself a group (fired at its offset as a control cue, which then starts a playlist/all-together of its own) leaves those grandchildren playing after the scene's stop. If nested groups inside timelines are intended to be unsupported, the validator should say so; if supported, the stop should walk the subtree (the engine already has Descendants in ShowHost.Execution.cs).

INFO N-11 · Test infrastructure: suites are not parallel-host safe, and one clock test is load-flaky

Running the whole solution in a single dotnet test produced (a) one failure in S.Media.Core.Tests's clock timing group that passes in isolation, and (b) one aborted test host buried in ALSA "unable to open slave" spam — device-touching suites racing each other for the audio server. The previous review dodged this by running assemblies sequentially. Worth making the constraint executable rather than tribal: a .runsettings with MaxCpuCount=1 at the solution level (or an env guard in device-touching fixtures that falls back to the null backend when the device is busy), and marking the timing tests with the existing MFP_TIMING_TESTS opt-in so a loaded CI box doesn't fail on scheduler jitter.

INFO N-12 · This machine's system .NET is broken; local dev currently depends on it not being noticed

/usr/share/dotnet has SDK 10.0.111 but only host runtime 10.0.10 — every dotnet invocation dies with "You must install or update .NET" (a distro partial-update; cachyos shipped the SDK bump before the runtime). This review installed SDK 10.0.400 locally to proceed. Worth fixing the box (sudo pacman -S dotnet-runtime to pull 10.0.11, or reinstall the bundle), and worth noting that global.json's rollForward: latestFeature + allowPrerelease: true means CI and dev boxes can quietly build on different feature bands (the previous review's F-16 makes the same point; concur — pin a tested band and update it deliberately).

INFO N-13 · Reference/ drift, re-checked

Confirming and extending F-18 with current deltas: Avalonia-12.1.0 vs pinned 12.1.1, Mond-0.11.2 vs pinned 0.12.0, YoutubeExplode-6.6 vs 6.6.1, Vortice.Windows-1.9.143 vs 3.8.3, plus unpinned "-master" snapshots (SDL3-CS-master, AvaloniaEdit-master, Xaml.Behaviors-master) whose directory names carry no identity at all. UI/UX review — with rendered evidence

Captured via Avalonia headless + Skia from the real views over the seeded fixture project (no engine). The previous review could not obtain pixels on its host; these are actual renders.

CUES workspace: transport bar, cue tree with playlist/timeline groups, inspector, Active panel, status bar.

What works well

  • Density with hierarchy. The cue tree's number/label/source/fade/len/dB columns plus kind badges (loop/offline/patch/MIDI/playlist/timeline) read at a glance; "14 cues · 18 in show" and "0 sounding · scope never hides these" are exactly the kind of honest micro-copy operators trust.
  • Inline pedagogy. Panels teach their own rules ("the only destinations cues can see", "delete cleans up its cue sends automatically - one undoable edit"). This is the best-documented show-control UI I have reviewed.
  • Failure surfacing. The Audio inspector's red "nothing - silent" row state, and the Targets LEARN pane's disabled-state explanation ("select a source first"), both answer the question before it is asked.

Observations (smaller than findings)

  • GO hit target. GO is one small button among nine in the top bar. Keyboard/Space is clearly the primary path, but during a fumble the mouse fallback matters; consider letting GO grow (taller row or double-width) — QLab-style prominence — or an opt-in "big transport" mode. (The previous review's F-09 title-bar crowding point is adjacent; solve together.)
  • Truncated placeholders. In the Video inspector the watermarks clip mid-sentence: "1920×1080 · empty follows the" and "used when the composition has no id". Watermarks that can't fit should be short, with the full sentence as a tooltip.
  • Source/target column truncation in the cue tree ("track-…", "Foldback dow…") — fine if tooltips exist; verify.
  • Launcher recovery banner renders (in the unbound harness) as bare RECOVER/DISCARD with no session identity; ensure the bound version always names the project and capture time — a recovery offer the operator can't identify teaches them to press DISCARD.
  • Settings window rendered with overlapping section text in the harness (section headers colliding with body copy, "CLIP RESETS" clipped). This may be an artifact of the harness DataContext — worth one manual check at 1000×680 and at 125/150% scaling; if it reproduces, the settings list wants to be a virtualized scrollable stack with min-height rows.
  • Two LEARN affordances on the Targets tab (the LEARN header pane + the BIND/LEARN buttons) — consider one labelled flow ("LEARN → press control → FIRES → BIND") to remove the ambiguity of which LEARN to press first.

Performance & simplification

  • Audio path: leave it alone. FrameAlignedFloatRing (CAS-guarded flush, whole-frame alignment), the SIMD channel map, lock-free terminal-clock republishing, and the bounded producer rings are correct and fast; the checked-in benchmarks (previous review's table) support that. Add regression envelopes, don't rewrite.
  • The real CPU hotspots this pass found are on the UI thread, not in the engine: N-05's render-path allocations and full-repaints, and N-08's fine-grained polling. These are cheap wins that improve the operator experience directly (smooth playhead on laptops, no GC hitches during a scrub).
  • CPU compositor budgets: concur with F-07's measured verdict; nothing in this pass contradicts it. The tiering recommendation there (explicit supported tiers + capability truth per F-14) remains the right frame.
  • Simplification: the strongest candidates are not the big coordinators (they are partial-split with clear seams and excellent comments) but the duplicated idioms: two remote-API server lifecycles (HaCue2/HaPlay — F-05 proposes the shared bounded host; concur), two dB↔linear conversion sets in ShowHost alone (Linear/LinearToDb plus three inline Math.Pow copies — one GainMath helper in Core would remove ~6 restatements of the silence-floor rule), and the twin AutomationRun/VisualizerAutomationRun lease implementations which are line-for-line duplicates ripe for one shared base.

Merged roadmap

The earlier review's phase structure is right; this pass's items slot into it rather than reshaping it.
