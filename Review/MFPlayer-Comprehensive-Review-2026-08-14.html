MFPlayer engineering, playback & operator UX review

A whole-repository assessment with emphasis on the reusable media framework, HaPlay, and especially HaCue2. The implementation is substantially stronger than its public packaging and documentation imply; the most urgent work is concentrated in release truth, two correctness races, remote-service lifecycle, and CPU fallback budgets—not a wholesale rewrite.

Executive verdict

Strong runtime engineering, blocked distribution truth, focused correctness work

This is not a fragile prototype. The repository has unusually good ownership documentation, architecture tests, AOT discipline, lifecycle regression coverage, bounded real-time queues, and operator-oriented UI work. It is also not yet a framework that an external user can install from the advertised package surface, and HaCue2 has two code-path defects capable of losing confidence in saved state or cancelling the wrong cue.

What is already strong

Explicit registries and native lifetimes, a single show-session dispatcher, frame ownership, pooled hot paths, architecture graph enforcement, warning-as-error/AOT gates, broad regression tests, and launch smokes. HaCue2’s direct placement/warp and absolute-time automation UX are particularly well judged.

What blocks a release claim

S.Media.Full cannot restore from public NuGet because it requires a repository-local FFmpeg.AutoGen 9.0.0. Linux release jobs fetch a mutable FFmpeg master artifact while the emitted manifest, docs, and native SBOM say “8.1”.

Where to invest next

Fix package/native provenance as one program; introduce version-aware HaCue2 persistence; scope active cue cancellation; qualify the exact HaCue2 upload bytes; then bound its remote transport and establish CPU-fallback tiers before decomposing large coordinators.

How the review was performed

Static inspection

Mapped the solution and project-reference graph; traced registry/native ownership, decode/player/session/compositor paths, output leases, project restore, cue dispatch, persistence, remote APIs, and application composition roots. Reviewed current XAML and view-model paths rather than treating older plans as current truth.

Executable validation

UX review

Inspected full app shells, command priority, responsive behavior, focus/accessibility tests, editing models, dialogs, failure/status surfaces, localization and operator safety. A real desktop launch succeeded, but capture on this host produced an unusable black screenshot; visual conclusions therefore combine live smoke, headless rendered-control tests, and layout inspection rather than a pixel-perfect screenshot review.

Upstream check

Compared central pins and ignored reference snapshots with official package/release sources. The checks were current on 2026-08-14; they should be refreshed automatically rather than copied indefinitely into documentation.

Evidence labels used below: confirmed means the code path or command directly demonstrates the condition; measured is observed test, launch, or benchmark data; design risk is strongly supported but needs an operational reproduction; coverage gap identifies missing proof, not a demonstrated runtime failure.

Limitations

  • No Windows runner, Android SDK/workload, NDI receiver, projector hot-plug rig, physical MIDI/OSC controller, multi-channel audio interface, or real MMD corpus was available locally. Detailed findings · framework & release

Media framework libraries

F-01CriticalConfirmed

The advertised framework package graph cannot restore from public NuGet

Observation. The central package graph requires FFmpeg.AutoGen 9.0.0, explicitly notes that it is not on nuget.org, and resolves it through the repository-local ./packages feed. The produced S.Media.Full 1.1.0 package carries that dependency. A consumer without this checkout therefore has no source for one of the graph’s required packages.

Direct reproduction. Restoring S.Media.Full.csproj with a fresh global-package cache and nuget.org as the only source failed with NU1102: 61 versions were found and the nearest was 8.1.0. Packaging S.Media.Core and S.Media.Full inside the repo succeeds, which shows why the problem is easy to miss locally.

Long-term fix

Choose one supported distribution contract: (1) align the public framework with an official FFmpeg.AutoGen release; (2) publish the generated fork under a unique, owned package ID and documented feed; or (3) internalize the generated bindings into the first-party FFmpeg binding package. Do not publish a private rebuild under an upstream ID/version. Add an end-to-end package job that packs every first-party package, restores a blank consumer from a staged feed plus nuget.org, compiles/runs a minimal player, validates symbols/docs/license metadata, and publishes only from a signed tag.

Acceptance. A machine with no clone, empty NuGet cache, and only documented feeds can install S.Media/S.Media.Full, build, and run the sample; the exact published nupkgs are retained as CI artifacts and provenance-linked to the tag.

Evidence

  • Directory.Packages.props:34–43 — local-only 9.0.0 pin.
  • nuget.config:3–10 — repo-local package source.
  • Doc/Packages.md:1–34 — packages described as published/installable.
  • Official NuGet version list — current public package is 8.1.0.
  • No dotnet pack, staged-consumer restore, or nuget push step exists under .github/.
F-02HighConfirmed

Mutable FFmpeg master is shipped under stable-8.1 provenance

Observation. Linux CI downloads releases/download/latest/ffmpeg-master-latest… and checks only for the current libavformat.so.63 name. That URL is mutable. Meanwhile the required-native manifest says “FFmpeg 8.1”, the dependency matrix says “8.1 / avcodec-62”, the release-tier document says “8.1”, and the SBOM generator labels every FFmpeg binary n8.1. The central binding is a custom “9.0.0” targeting ABI 63. These claims cannot all describe the same binary.

The official FFmpeg release index currently contains 8.1.2 and snapshots, while official FFmpeg.AutoGen is 8.1.0. The repository is intentionally consuming a future/master ABI snapshot, not an FFmpeg 9 stable release. That can be legitimate, but its identity must be exact and immutable.

Long-term fix

Create one machine-readable native lock (for example native-dependencies.lock.json) containing upstream project, exact tag/commit or immutable artifact URL, SHA-256, expected ABI/version function result, license, redistribution policy, and supported RIDs. Generate package pins, docs, manifests, CI download steps, and SBOM labels from it. Verify every FFmpeg library’s runtime version/ABI—not just filename presence—and fail on drift. If master is required, call it a dated snapshot tied to a commit/digest.

Acceptance. Changing any FFmpeg URL, hash, ABI, binding version, documentation claim, or SBOM label independently breaks CI; the uploaded artifact’s queried versions and hashes match the generated provenance record.

Evidence

  • build.yml:91–115, 487–505 — mutable master/latest download.
  • linux-x64.txt:1–11 — 8.1 label.
  • Native-Dependencies.md:7–18 — avcodec-62 and stale SDL version.
  • generate-native-sbom.sh:14–35 — hardcoded 8.1 provenance.
  • check-native-versions.sh:1–145 — version gates omit FFmpeg.
  • Official FFmpeg release index.
F-04HighConfirmed code path

Targeted stop can cancel an unrelated ordinary in-flight cue fire

Observation. CueRunner stores a single anonymous _activeFireCts. Both CancelFiresForCue(cueId) and CancelFiresForGroup(groupId) unconditionally call CancelActiveFire() before applying identity-aware matching only to prepared scheduled batches. ShowSession.StopCueAsync and group StopAsync call those methods. If cue A is in pre-wait/open while the operator stops unrelated cue B or group B, A is cancelled.

Existing scoping tests correctly protect scheduled batches, but they park FireCuesIndependentScheduledAsync; they do not cover the ordinary _activeFireCts path. The nearby comments promise targeted semantics that the active-fire representation cannot express.

Long-term fix

Replace the anonymous CTS with an active-fire record containing cue IDs, affected runtime group IDs, generation, kind, and CTS. Targeted stop cancels only a matching record; panic/load/dispose retain blanket cancellation. If simultaneous fires are introduced for F-08, make this an indexed set rather than another single slot.

Acceptance. Deterministic tests block cue A in pre-wait and in cancellable open, stop unrelated cue/group B, then prove A fires. Matching cue/group stop must cancel it; panic/load/dispose must cancel all. Include parallel list and scheduled-batch combinations.

Evidence

  • CueRunner.cs:24–44, 191–211, 475–517.
  • ShowSession.Stops.cs:31–46, 130–154.
  • CueFireScopingTests.cs:5–115 — scheduled-only coverage.
F-07HighMeasured artifact

Common CPU fallback shapes miss a 60 fps budget at 720p

Observation. The checked-in BenchmarkDotNet results report 21.21 ms for the representative four-layer 1280×720 deck shape, versus a 16.67 ms 60 fps budget. One bilinear layer costs roughly 28–36 ms and bicubic 69–92 ms. Only nearest/source/identity reaches the specialized 222 µs path. Allocations are already excellent (312 B), so the bottleneck is compute/memory bandwidth, not GC.

The compositor clears the full rented output before examining layers, even when the first opaque source layer provably overwrites the canvas. The generic path performs inverse mapping, sampling, effects, and blend dispatch per pixel. CPU fallback is valuable for tests, servers, and degraded operation, but the supported quality/frame-rate envelope is currently implicit.

Long-term fix

Define explicit CPU fallback tiers and budgets first. Then skip the clear when coverage analysis proves a full overwrite; specialize common bilinear/source-over/effect chains by rows or tiles; vectorize kernels; cache transform increments; and parallelize tiles only where the crossover is measured. Default operational apps to GPU and surface a conspicuous degraded-mode/capability warning rather than silently promising the same output class.

Acceptance. CI tracks 720p/1080p/4K at 1/4/8 layers, nearest/bilinear, identity/scale/rotate, source/source-over and built-in effects; named supported tiers stay inside p95 frame budgets on a pinned reference machine with a reviewed regression threshold.

F-08MediumConfirmed design

One global fire lock creates cross-list head-of-line blocking

_fireLock serializes every ordinary fire and holds across cue selection, authored pre-wait, media open, fire, and cursor advance. This protects duplicate GO/cursor correctness, but an unrelated list’s GO can wait behind a cold or slow open—up to the 30-second batch preparation bound in some paths. The UI dispatcher remains responsive; operator action latency does not.

Long-term fix

Use per-runtime-group serialization with stable multi-lock ordering for multi-group batches, or a two-phase model: reserve identities/cursors, prepare off-lock, then perform a short generation-checked commit. Preserve exactly-once GO and stale-generation rejection. This work should be designed together with F-04 because multiple active fires need identity-aware cancellation.

Acceptance. A blocked open on list A does not delay GO on unrelated list B; two simultaneous GO commands on the same list cannot double-fire; overlapping batches remain deadlock-free; latency histograms expose select, prepare, commit, and wait phases.

Evidence

  • CueRunner.cs:40–60, 191–224, 531–558.
  • Current comments explicitly note that a wedged open once held the lock for every GO.
F-11MediumMeasured structure

Session and UI coordinators have grown beyond comfortable feature boundaries

The dependency graph is layered, but behavioral ownership is concentrated. Examples: HaCue2 InspectorViewModel is 3,935 lines, CuesViewModel 3,473, VideoViewModel 2,578; framework ClipCompositionRuntime is 3,692 and the primary ShowSession.cs is 2,238 before its partials; HaPlay’s MediaPlayerViewModel is 2,439 plus a 1,533-line session partial, CueNodeViewModel 2,105, CueShowSessionCoordinator 1,964, and CuePlayerView.axaml 1,680. There are 331 public declarations across ShowSession*.cs, including nested public members/types.

Large files are not a defect by themselves. Here they increase the chance that save, live-edit, output lease, transport, visualizer, audition, diagnostics, and view state changes interact through implicit sequencing.

Long-term fix

Preserve one dispatcher and one transaction boundary, but extract narrow, testable facades: transport/fire, composition/output leases, audition/taps, live-edit/control ownership, and diagnostics. Split HaCue2 inspector behavior by feature editor session/tab; split HaPlay workspaces into lifecycle-owned subgraphs. Avoid “service per method”: each extraction needs a clear state owner, contract tests, and explicit disposal.

Acceptance. Each feature has one owner and bounded public contract; adding a cue type or output no longer edits several thousand-line coordinators; architecture tests enforce the new edges; concurrency/lifecycle integration tests continue to cross the real composition root.

F-13MediumConfirmed API

Several public API contracts are documented but still surprising to consumers

  • IMediaClock.Stop() is currently exactly Pause(); common transport expectations make that a semantic trap beside a separate Reset().
  • TryOpenVideo/TryOpenAudio return false only when no provider is selected; a selected provider’s open failure throws. XML documentation is clear, but the conventional “Try” shape suggests no-throw outcome semantics.
  • MediaPlayer.AttachConsoleCancelKeyPress installs a static event handler capturing a CTS and returns no unsubscription handle.
  • MediaRegistry correctly unwinds native lifetimes in reverse order but silently swallows every disposal/rollback failure, leaving no health signal for a leaked native runtime.

Long-term fix

Design a vNext surface rather than changing behavior in place: deprecate or define Stop as an atomic pause+reset; steer consumers to the already-better atomic OpenAsync(MediaOpenRequest) and return a structured resolution/open result where needed; make host event subscriptions return IDisposable and move console helpers to tools; aggregate native-release failures into diagnostics/health while keeping Dispose non-throwing.

Acceptance. API docs and names predict exception/state behavior without caveats; compatibility shims are obsolete-marked with migration examples; repeated console host creation does not retain CTS instances; teardown failures appear in structured diagnostics.

Evidence

  • MediaClock.cs:325–364.
  • IMediaRegistry.cs:30–68.
  • MediaPlayer.cs:511–519.
  • MediaRegistry.cs:138–184.
F-14MediumConfirmed contract

GPU-only effects silently become pass-through on CPU fallback

The extension contract permits an effect with no CPU kernel and explicitly skips it in CpuVideoCompositor. Built-in HaCue2 effects currently supply CPU implementations, but a future/plugin effect can produce a materially different show when GPU initialization fails—precisely when an operator is already diagnosing degraded output.

Long-term fix

Add compositor capability negotiation and preflight. The show compiler/runtime should know whether every active effect has a valid implementation on the selected backend. Policy can be fail-closed, disable the affected output, or allow an explicitly acknowledged degraded render, but it must never be silent. Include the chosen backend and unsupported effect IDs in output health.

Acceptance. A GPU-only test effect on CPU fallback yields a deterministic validation issue and conspicuous runtime state; the operator can identify the affected cue/output and policy; supported effects retain visual parity fixtures across CPU/GPU.

Evidence

  • VideoLayerEffectDescriptor.cs:15–30.
  • CpuVideoCompositor.cs:148–160.
F-17MediumCoverage gap

Managed supply-chain and workflow-integrity checks are manual

The single workflow is extensive, but there is no visible Dependabot/Renovate configuration, CodeQL/static security workflow, managed dependency/license/SBOM gate, or public package consumer gate. Actions are referenced by mutable major tags and no top-level least-privilege permissions declaration is present. Detailed findings · flagship cue authoring

HaCue2

UX strengths worth protecting. HaCue2 has a clear one-window model, visually dominant GO and hold-to-panic behavior, separate scheduling/trigger arms, output health doorway, lock mode, direct placement and warp manipulation, scrollable/zoomable absolute-time automation with waveform and exact fields, source preparation/status, and unusually useful headless render/focus/accessibility tests. The right inspector already collapses at laptop width and can be restored. Recommendations below extend this operator model rather than replacing it.
F-03HighConfirmed code path

An edit during Save can be absent from disk while the document becomes clean

Failure sequence. HaCueProjectFile.SaveAsync synchronously serializes the live project, then awaits an asynchronous write to a fixed sibling .tmp. The UI remains editable. If an edit occurs after serialization but before the write completes, the file contains the old snapshot. On success, ShellViewModel.SaveToAsync calls Journal.MarkSaved() against the now-newer live project, moves the saved pointer to its current undo entry, clears the out-of-stack dirty flag, and clears recovery. The title/close path can therefore report clean while the edit is not on disk.

A second Save can also target the same fixed path.tmp. The final rename is atomic within a filesystem, but the write has no unique temp, generation/order, durable flush, or one-deep backup. HaPlay already demonstrates a stronger generation/hash/coordinator and unique write-through temp pattern.

Long-term fix

Build one shared project persistence component. Capture an immutable/versioned snapshot and journal revision; serialize that snapshot off the UI thread; serialize save requests through a generation-aware queue; write a unique same-directory temp with flush/write-through; atomically replace while retaining a known-good backup/recovery generation; and call MarkSavedIfCurrent(revision, hash). If edits occurred after the snapshot, saving may still succeed but the document must remain dirty and recovery must remain.

Acceptance. An injected slow writer allows an edit between snapshot and completion; the file contains the captured snapshot and UI stays dirty. Double Ctrl+S cannot collide. Crash/fault injection at every write/flush/move stage leaves either the prior or new valid project, never a false-clean document.

F-05HighConfirmed design

The HaCue2 remote server has unbounded handlers and an unbounded shutdown drain

Every accepted HttpListenerContext creates a new Task.Run, retained in a HashSet, with no concurrency admission, header/query limit, request deadline, rate control, or cancellation linked to server life. Unauthorized peers still consume handler resources. Handler dispatch can await transport operations such as GO/fire/open. Shutdown closes the listener and then waits indefinitely for every captured handler; a stuck transport call can hang application teardown. Unexpected exception text is also returned directly to a remote client.

HaPlay’s independent implementation already contains the missing transport mechanics: max 32 requests, input limits, linked 30-second deadlines, bounded two-second drain, safe abort, and structured logging. The route dispatchers must remain app-specific, but two HTTP lifecycle implementations should not drift.

Long-term fix

Extract an AOT-safe bounded HTTP control host with pluggable route dispatch. Enforce concurrency/backlog admission, early auth and size limits, per-request deadlines, server-life cancellation, bounded drain, safe client errors plus correlation IDs/full internal logs, constant-time token checks, and explicit idempotency/replay semantics for action commands.

Acceptance. Load tests cannot exceed the configured handler count; oversized/unauthorized traffic is rejected cheaply; a deliberately hung dispatch cannot delay shutdown beyond the drain budget; clients never receive internal exception details; both apps share the same transport tests.

Evidence

  • RemoteApiServer.cs:46–55, 121–185, 366–404.
  • HaPlay RestApiServer.cs:22–33, 195–337, 358–401 — stronger existing reference.
F-06HighConfirmed

The exact uploaded HaCue2 artifact is never launch-gated

The build job AOT-publishes HaCue2 and attempts a first-frame smoke, but both Linux and Windows launch steps use continue-on-error: true and the publish lacks the final staged native set. The artifact job later stages natives and gates manifest presence, loadability, and selected versions, then immediately uploads hacue2-publish. HaPlay launches that exact upload directory on both platforms and requires backend enumeration plus a first frame.

Long-term fix

Turn artifact qualification into one reusable script/job applied to every shipped desktop head. Launch the exact post-staging/post-strip directory, isolate settings/cache, require registry/backend enumeration, shell creation, first rendered frame, and normal teardown, then optionally open a generated minimal media/show fixture. Upload only qualified bytes.

Acceptance. Removing a required app-local native, breaking the HaCue2 composition root, failing GL creation, or wedging teardown fails the artifact job before upload on Linux and Windows; the hash of the tested directory matches the uploaded artifact.

Evidence

  • build.yml:308–349 — best-effort HaCue2 launch.
  • build.yml:780–809 — exact HaPlay artifact gate.
  • build.yml:860–926 — HaCue2 validate then upload, no launch.
F-09MediumDesign risk

Long project identities can crowd HaCue2’s fixed-priority title bar

The shell supports a 900 px minimum width. Its title bar is a single grid containing File, an auto-sized project filename with no maximum/trimming, the four-view selector, mode, Lock, Settings, and Diagnostics. A long filename or longer localized copy can consume the auto column and push safety/diagnostic controls outside the usable width. The main Cues inspector has a responsive collapse test at 960 px; the full shell title bar does not have equivalent long-content/DPI coverage.

Long-term fix

Define responsive command priority. Bound and middle-ellipsize the project identity while preserving the full path tooltip; retain mode/Lock and primary view switching; move lower-priority Settings/Diagnostics into a labelled overflow at compact thresholds, or use icon+accessible-name variants. Test the full ShellWindow, not only CuesView.

Acceptance. At 900×640 and 125/150/200% scaling with a long Unicode filename and expanded translations, Lock, mode, current view, File, and an overflow/diagnostics route remain visible, focusable, non-overlapping, and screen-reader named.

Evidence

  • ShellWindow.axaml:9–15, 31–93.
  • AccessibilityAndResponsiveTests.cs:14–67 — useful Cues-only coverage.
F-21MediumConfirmed design

HaCue2 operator copy is hardcoded rather than localization-ready

HaCue2’s XAML and view models embed English labels, hints, tooltips, error sentences, and status grammar directly; no resx/string resource surface exists. This makes translation expensive, prevents long-string layout tests, and encourages terminology drift across Settings, Diagnostics, Inspector, and engine faults. HaPlay is not fully translated, but it has a central Strings.resx, generated accessor, and raw-literal ratchet tests.

Long-term fix

Introduce typed string resources by semantic domain, not one giant unstructured list. Separate operator-facing copy from log/developer diagnostics; use parameterized messages and plural-aware formatting; migrate screen by screen with a literal-lint ratchet. Add a pseudo-localization culture that expands strings and introduces non-ASCII/RTL markers to drive layout tests.

Acceptance. New user-visible literals fail lint; the complete shell renders under 30–40% expansion and pseudo-localization; terminology such as fire/go/standby/program/audition/lock is centrally defined.

Evidence

  • No .resx or string resource/accessor exists under UI/HaCue2*.
  • ShellWindow.axaml and InspectorPane.axaml embed operator copy.
  • HaPlay/Resources/Strings.resx and RawStringLiteralLintTests.cs are a reusable pattern.
F-22LowConfirmed

Lock-mode copy contradicts the intentionally writable note field

The Lock tooltip says “Read-only document”, while ProjectJournal explicitly permits note-property commands under lock and the Note pane says notes remain writable. The behavior may be exactly right for show operation; the explanation is not.

Long-term fix

Rename the state to “Authoring locked” and say “Cue structure and show-critical settings are locked; notes remain editable. GO, preview, and audition are unchanged.” Visually identify the performance-note exception. If strict read-only is also needed, make it a separate, explicit mode.

F-15MediumConfirmed policy

HaPlay LAN control deliberately permits no-token operation

LAN binding is an explicit choice and the UI shows an unmistakable warning, both good safeguards. The server nonetheless treats an empty token as authorization for every request. “Closed venue LAN” is often an aspiration rather than a security boundary; guest Wi-Fi bridging, misconfigured VLANs, laptops, and controller software make a fire/stop API consequential.

Long-term fix

Enabling LAN should mint and require a high-entropy token by default, with copy/QR/controller onboarding. If tokenless Companion compatibility is essential, expose a separate time-bounded “Open LAN” exception with confirmation, persistent high-visibility status, listener scope, audit log, and optional source-address allowlist. Never silently preserve tokenless mode through an upgrade.

Acceptance. Fresh LAN enablement is authenticated; tokenless mode requires an explicit exception and cannot be mistaken for the default; remote actions record source/correlation/result without logging secrets.

Performance & simplification

What to optimize—and what not to disturb

Audio hot paths are in good shape

The existing wide dense matrix benchmark scales from 6.11 µs at width 8 to 219.56 µs at width 64 with zero managed allocation. The program-sum maximum topology reports 2.033 ms, also with zero allocation. Preserve the ring/SIMD/whole-frame design and add regression envelopes; there is no evidence for a disruptive rewrite.

CPU video is the clear hotspot

Prioritize fast-path coverage, redundant clear removal, row/tile specialization, and backend capability truth. Do not chase micro-allocations while 720p generic kernels take tens of milliseconds.

Startup needs sequencing, not deletion

The expensive work—XAML resource creation, backend/device discovery, session setup—is valuable. Reorder it around first interaction, publish readiness, share enumerations, and measure phases before removing capability.

Simplify ownership surfaces

Decompose large coordinators around state ownership and transaction boundaries. Avoid additional global registries, duplicated remote/persistence transports, or a generic service layer that merely moves methods without shrinking coupling.

Sequence work by safety and shared foundations

The order matters. Closing documentation alone before provenance produces new drift; splitting coordinators before defining ownership produces more coupling; optimizing CPU kernels before defining supported tiers makes performance work unbounded.
